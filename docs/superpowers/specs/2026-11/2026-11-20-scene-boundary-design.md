# Межа поточної сцени за будь-якого горизонту (#231)

## Для власника

### Мета

Письменник і планувальник не пишуть біти наступних сцен, коли бачать їхні плани. Запит, що містить хоча б один план майбутньої сцени, завжди прямо каже: «реалізуйте лише біти поточної сцени».

### Що зміниться для тебе

- У режимі горизонту «Поточна та всі наступні сцени» (типовий) бриф, чернетка, повна редактура й переписування за коментарями отримують секцію «МЕЖІ ПОТОЧНОЇ СЦЕНИ» щоразу, коли в запиті є план наступної сцени. Раніше ця секція була лише в режимах «N наступних» і «лише поточна» або за непорожнього орієнтира фіналу.
- В останній сцені твору в режимі «усі» майбутніх планів немає, тож секції, як і раніше, немає (якщо не задано орієнтир фіналу).
- Режими «N наступних», «лише поточна» й орієнтир фіналу дають той самий запит, що й зараз.
- Наявні бриф, чернетки й проза від оновлення не стають застарілими. Щоб виправити вже написану сцену, перебудуйте її бриф і чернетку.
- Контекст сцени для чату (MCP) майбутніх планів не містить і не змінюється.
- Нічого незворотного: зберігання, знімки й формат відповіді моделі не змінюються.

### На чому стоїть рішення

- У творі власника всі ролі мають горизонт `all`, орієнтир фіналу порожній, чернетка сцени N має серед `input_refs` версію плану сцени N+1 і реалізує його біти; бриф сцени N узяв локацію з плану N+1 `[проба]` (П1).
- `build_context` додає `horizon_instructions` лише коли `horizon_future_count(settings)` не `None` (обмежені режими) або коли `ending_goal` непорожній `[проба]` (П2, П3).
- CONTEXT-005 так і формулює: межу «SHALL явно обмежувати» лише обмежені режими й запит з орієнтиром. Режим `all` з майбутніми планами лишився без межі — це вада вимоги, а не лише коду `[виведення]`.
- Секцію отримують лише brief, draft, edit (повна редактура) і rewrite: memory і patches/diff повертаються раніше й майбутніх планів не мають `[проба]` (П4).
- Розмір S за оцінкою власника `[вимога власника]`.

### Ключові рішення

1. **Умова — наявність у запиті плану хоча б однієї наступної сцени (або орієнтира фіналу), а не режим горизонту.** Відкинуто: змінити типовий режим на `next_n`. Це змінило б, які плани бачить модель, і не виправило б наявні налаштування `all`.
2. **Текст секції той самий (`horizon` + `horizon_not_last`/`horizon_last`).** Відкинуто: новий сильніший текст із часом кінця сцени. Він змінив би й обмежені режими; окремий випадок, якщо цього не вистачить.
3. **Попередження `HORIZON_LIMIT_WARNING` лишається лише для обмежених режимів.** Воно пояснює саме обмеження горизонту, а в режимі `all` нічого не обмежено.

### Що стане гірше

- Запити в режимі `all` трохи довші (≈ 200 символів).
- Хеш складеного запиту в режимі `all` змінюється: зафіксовані в тестах хеші треба оновити.
- Інструкція не гарантує поведінки моделі; вона лише прибирає відсутність межі.

### Оцінка

- Власник: **S**.
- Автор: **S**, один PR, ≤ 3 задачі. Розподіл:
  - умова в `build_context` — ~15%;
  - тести (режими, остання сцена, хеші) — ~45%;

- Дешевшого варіанта немає: обхід (горизонт «N наступних» або орієнтир фіналу) уже доступний без коду.

## Тіло

### Проби

**П1. Твір власника (лише GET).** Налаштування твору: `future_plan_mode=all` для всіх ролей, `ending_goal` порожній. Чернетка сцени N (джерело — запуск моделі Obscura) має в `input_refs` поточну версію плану сцени N+1; друга половина тексту реалізує біти N+1 майже по порядку. Бриф N у constraint «Локація» має місце дії з плану N+1. Кінець сцени N і початок N+1 мають той самий час; останній біт N переходить у перший біт N+1.

**П2. Код.** `generation/context.py`: цикл `selected_plan_scenes` додає секції `future_plan`; далі `count=horizon_future_count(settings)`; `horizon_instructions` додається, коли `count is not None`, або після `ending_goal`, коли `count is None`.

**П3. Тимчасовий тест на тестовому творі з 3 сцен.** Бриф сцени 1: `all` — план сцени 2 є, «МЕЖІ ПОТОЧНОЇ СЦЕНИ» немає; `next_n=1` — план є, межа є.

**П4. Етапи.** Гілка `memory` і `edit` з `patches/diff` завершуються до секцій майбутніх планів; `writing_context` (MCP) не викликає `selected_plan_scenes`.

### Поведінка

Після циклу майбутніх планів: `future=` кількість доданих планів сцен з позицією більшою за поточну. Секцію `horizon_instructions(scene,len(scenes),language)` додано один раз, якщо `count is not None`, або `future>0`, або `ending_goal` непорожній. Порядок секцій для обмежених режимів і для орієнтира фіналу не змінюється: у режимі `all` без орієнтира межа стоїть одразу після майбутніх планів; з орієнтиром — після нього, як зараз.

Знімки не змінюються: у режимі `all` селектор порядку `all` уже містить усі сцени, тож вибір між `horizon_last` і `horizon_not_last` захищено. Fingerprint контексту для `all` змінюється; заморожені спроби не переписуються.

### Scenarios (SPEC.MD, CONTEXT-005)

- **S06 — Межа за всіх майбутніх планів.** GIVEN горизонт `all`, порожній орієнтир і сцена, що не остання. WHEN будується бриф, чернетка, повна редактура чи переписування. THEN запит містить «МЕЖІ ПОТОЧНОЇ СЦЕНИ» з «Поточна сцена не остання» рівно один раз. AND остання сцена в `all` без орієнтира секції не має; `next_n`, `current` і запит з орієнтиром мають той самий текст, що до зміни; memory і patches/diff секції не мають.

Traceability: S06 → pytest у `tests/generation/test_story_horizon.py`.

### Документація

- SPEC.MD CONTEXT-005: межа діє за будь-якого режиму, коли в запиті є майбутній план або орієнтир; усунено відхилення: режим `all` не мав межі.
- Сайт `writing-tools.md` (uk/en), розділ «Горизонт»: речення про межу поточної сцени.
