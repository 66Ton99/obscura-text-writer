# Редактор завдання письменнику без ручного JSON (#213)

Дата: 2026-11-20
Статус: затверджено 2026-11-20 (власник доручив специфікацію й реалізацію на ніч одним рішенням)
Spec-review: codex/gpt-6.1-sol @ c8327c1 (author: claude) — 2 findings: 2 fixed, 0 rejected

## Для власника

### Мета

Автор правит завдання письменнику (бриф сцени) як звичайну форму: мета, біти, обмеження, пропозиції змін. Одна пряма лапка чи перенос рядка більше не ламають збереження.

### Що зміниться для тебе

- **На вкладці «Завдання» замість сирого JSON — форма:**
  - мета;
  - нумеровані біти: кожен у власному полі, з кнопками «вище», «нижче», «вставити перед», «видалити» і «Додати біт» у кінці;
  - список обмежень;
  - список пропозицій змін.

  Номери бітів показуються біля полів і в текст біта не входять. Вставка біта на початок чи в середину, видалення або переміщення перенумеровують решту, не змінюючи текстів.
- **Кнопка «Розширений JSON»** показує той самий текст, що й раніше; «Звичайний вигляд» повертає форму. Незбережені правки при перемиканні не губляться. Якщо JSON у розширеному режимі зіпсовано, повернутися до форми не можна, доки його не виправлено (пояснення поруч).
- Збереження, конфлікт ревізії, історія версій і прийняття пропозиції завдання працюють як раніше. Історичну версію форма показує лише для читання.
- Якщо планувальник уже пронумерував біти («1. …», «2. …») по порядку, форма показує їх без цих номерів. Після першої правки у формі завдання зберігається вже без них.
- Знайомства (`introduced`) у формі не показуються: ними керує панель знайомств. При збереженні значення не губиться.
- Нічого незворотного: сервер, формат завдання, шлях через чат і відповіді моделей не змінюються.

### На чому стоїть рішення

- Формат зберігання (`WritersBrief` JSON), сервер, `save_stage_result` і відповіді моделей лишаються без змін; змінюється лише спосіб редагування `[вимога власника]` (#213).
- Номери бітів показуються в редакторі, але не входять у текст біта; вставка, видалення й переміщення перенумеровують решту `[вимога власника]` (#213).
- «Розширений JSON» лишається запасним виходом, як у таблиці пам'яті (MEMORY-FORWARD-S03) `[вимога власника]` (#213).
- `introduced` у формі не показується, але при збереженні не губиться `[вимога власника]` (#213).
- Збереження завдання вже йде з тексту буфера через `POST /api/scenes/{id}/brief` (`versions.js`), а сервер перевіряє його `WritersBrief.model_validate_json` і зберігає `model_dump_json()` `[проба]` (П1). Тож форма, яка пише JSON у той самий буфер, не потребує нового API.
- Письменник отримує завдання як JSON-текст під позначкою матеріалу (`context.py`, `head_brief`): біти — упорядкований масив, номери в тексті біта для нього не потрібні `[проба]` (П2).

### Ключові рішення

1. **Окреме поле для кожного біта, а не один текст із розділами.** Це відповідь на відкрите питання issue. Відкинуто: один текст із заголовками й рядками-бітами. Він повертає ту саму крихкість розбору, від якої задача позбавляє, лише в іншому синтаксисі.
2. **Буфер редактора лишається джерелом правди: це текст JSON.** Форма читає його й після кожної правки записує в нього новий JSON. Збереження, стан «не збережено», CAS, захист від втрати незбереженого тексту й історія працюють без змін. Відкинуто: окремий стан форми з власним збереженням — дублює механізм буфера (UI-002) і ризикує розходженням.
3. **Номери від планувальника знімаються лише тоді, коли всі біти пронумеровано по порядку з 1** («1. », «2) »…). Інакше текст біта показується як є. Знімання відбувається лише у формі й потрапляє в збереження тільки після правки автора. Відкинуто: знімати номер із будь-якого біта — «1990 рік…» чи навмисний номер у тексті зіпсувався б.
4. **Порожні поля живуть у буфері під час правки й відкидаються лише при збереженні.** Вставлене порожнє поле переживає перемикання на JSON і назад. Перед відправкою на сервер порожні біти, обмеження й пропозиції випадають. Якщо не лишилося жодного непорожнього біта, «Зберегти» неактивна з поясненням «Додайте хоча б один біт» (схема вимагає ≥ 1). Форма доступна й тоді, коли завдання ще немає або всі біти видалено: редагувати тимчасово неповне завдання можна, зберегти — ні.

Розглянуто стандартне: генератор форм за JSON Schema — відкинуто, бо полів чотири, а потрібна поведінка (нумерація, «вставити перед», знімання номерів, прихований `introduced`) все одно своя.

### Що стане гірше

- JSON, який зберігає форма, відформатований інакше, ніж ручний (сервер однаково зберігає компактний `model_dump_json`, тож у версіях різниці немає).
- Поля, яких схема не знає, форма не показує. Їх і зараз відхиляє сервер, тож втрат немає, але правити їх можна лише в розширеному JSON.
- Ще один шар інтерфейсу на вкладці «Завдання»: більше коду для підтримки й знімків для сайту.

## Тіло

### 1. Модуль `static/brief-form.js`

Чисті функції (тестуються в Node):

- `parseBrief(text) → {ok:true, model} | {ok:false, error}`: `JSON.parse`, перевірка типів (`objective` — рядок, `beats` — масив рядків, можливо порожній, `constraints`/`proposed_changes` — масиви рядків або відсутні, `introduced` — масив рядків, `null` або відсутній). Невідомі ключі → `{ok:false}`: форма не показує те, що не збереже. Порожній або пробільний текст (завдання ще немає) → порожня модель з одним порожнім бітом. Модель: `{objective, beats, constraints, proposed_changes, introduced, extra:false}`.
- `stripPlannerNumbers(beats) → {beats, stripped}`: якщо кожен біт `i` збігається з `^\s*(i+1)[.)]\s+`, повертає тексти без префікса й `stripped:true`; інакше — без змін.
- `serializeBrief(model) → string`: `JSON.stringify` з відступом 2. Порядок ключів: `objective`, `beats`, `constraints`, `proposed_changes`, `introduced` (лише якщо був у джерелі, з тим самим значенням). Порожні елементи зберігаються (буфер — повний стан форми), тексти не обрізаються.
- `briefForSave(text) → text`: якщо текст розбирається, повертає `serializeBrief` моделі без елементів, порожніх після `trim()`; інакше — текст без змін (розширений JSON зберігається як написано, сервер перевіряє його, як і зараз).
- `canSaveBrief(model)`: є хоча б один біт, непорожній після `trim()`.
- `moveItem`, `insertBefore`, `removeItem` над масивом.

### 2. Інтерфейс (`static/brief-editor.js`, встановлюється з `versions.js` поруч із `installMemoryTable`)

- Панель `#brief-form` у `#workspace-material` після редактора. Видна, коли `state.mode === 'brief'`, буфер розбирається `parseBrief` і не ввімкнено «Розширений JSON». Тоді `textEditor.visible(false)`.
- Поля:
  - мета — `textarea`;
  - біти — список `ol` з `textarea` на кожен біт, мітка номера `i+1.` і кнопки (`aria-label`: «Перемістити вище», «Перемістити нижче», «Вставити біт перед», «Видалити біт»), «Додати біт» у кінці;
  - обмеження й пропозиції змін — так само, без номерів.

  Усі тексти — через `value`/`textContent`.
- Кожна правка: `serializeBrief` → запис у буфер так, щоб спрацював наявний механізм «не збережено». Через `textEditor` додається метод `replaceText(text)`: для `textarea` він ставить `element.value` і викликає ті самі обробники введення, що й подія `input`. `write` для цього не годиться, бо скидає базову версію.
- Перемикач `#brief-advanced`: «Розширений JSON» / «Звичайний вигляд».
  - До JSON: показати редактор із поточним текстом буфера (він уже актуальний).
  - До форми: `parseBrief`. Якщо помилка — лишитися в JSON із повідомленням «JSON зіпсовано: …, виправте його або скасуйте зміни».
- Перемикання сцени чи вкладки повертає звичайний вигляд для наступного показу. Незбережений текст захищає наявний механізм буфера (UI-002), бо форма — лише вигляд буфера.
- **Історія** (`state.bufferOrigin === 'history'`): форма лише для читання — поля `readOnly`, без кнопок. Перемикач доступний.
- **Пропозиція завдання** (R20-BRIEF-REVIEW): прийняття працює з версією, а не з формою, тож нічого не змінюється. Правка пропозиції у формі перед прийняттям — те саме, що правка в JSON зараз (`source_brief_id` передається як і раніше).
- **«Зберегти»**: у формі, якщо `canSaveBrief` хибне, кнопка неактивна з підказкою «Додайте хоча б один біт». Збереження вкладки «Завдання» (`versions.js`, обидва шляхи `POST …/brief`) пропускає текст через `briefForSave`. Тож порожні елементи відкидаються саме тут, а буфер після успішного збереження отримує збережений текст наявним механізмом. Решта — наявна логіка.
- **Знімання номерів** (рішення 3): при розборі, якщо `stripped`, форма показує тексти без номерів, але буфер не змінює, доки автор не зробить правку. Тоді серіалізується вже модель без номерів.
- **«На весь екран»**: форма займає матеріал так само, як таблиця пам'яті.
- **Вузький екран**: кнопки бітів переносяться під поле.

### 3. Що не змінюється

`WritersBrief`, `routes_versions.py::manual_brief`, `accept-brief`, MCP `save_stage_result`, промпти, контекст письменника, CAS і формат версій.

### 4. SPEC.MD

Нова Requirement **BRIEF-FORM — Звичайний вигляд завдання письменнику** після R20-BRIEF-REVIEW:

- S01 — Форма й збереження: GIVEN завдання з метою, трьома бітами, обмеженням і `introduced`, WHEN автор правит біт із лапкою й переносом рядка і зберігає, THEN версія коректна, текст біта точний, `introduced` незмінний.
- S02 — Нумерація бітів: вставка біта на початок і в середину, переміщення й видалення перенумеровують мітки, тексти бітів не змінюються, номер не входить у текст.
- S03 — Розширений JSON: перемикання туди й назад зберігає незбережені правки; зіпсований JSON не дає повернутися до форми й пояснює чому.
- S04 — Номери планувальника й межі: біти «1. …/2. …» показуються без номерів, а буфер без правки лишається незмінним; історія показується лише для читання; без жодного біта «Зберегти» неактивна.

Технічний опис: модулі, буфер як джерело правди, `replaceText`, відомі обмеження (невідомі ключі лише в JSON).

traceability: S01–S04 → `tests/web/js/brief_form.mjs` (через pytest-обгортку) і `tests/web/browser/brief-form.spec.mjs`.

### Поправки (2026-11-20, під час реалізації)

1. **Порожні елементи лишаються в буфері й після збереження; `briefForSave` діє лише на текст запиту.** Буфер не можна змінювати ні перед збереженням, ні одразу після: «Зберегти й запустити» перевіряє, що буфер не змінився під час збереження, і без цього запуск відмовляв би (знахідка крос-рев'ю коду). Порожні поля зникають з форми після наступного завантаження завдання; сервер їх не отримує. `beforeSave` з обох шляхів збереження лише відмовляє без жодного непорожнього біта («Додайте хоча б один біт»).
2. **«Зберегти» в чистому стані лишається активною**, як і на інших вкладках; неактивною її робить лише відсутність біта. Браузерний тест перевіряє збереження через API, а не через стан кнопки.
3. **Знімок форми** знімає `scripts/capture_screenshots.py` (екран вкладки «Завдання» на десктопі, uk і en). Нейтральні завдання в скрипті стали змістовнішими: три біти й обмеження, узгоджені з чернеткою.
4. **Наявні браузерні тести, що вписують JSON у `#editor` на вкладці «Завдання»** (`brief-proposal.spec.mjs`, `save-and-run.spec.mjs`), спершу вмикають «Розширений JSON»: поле JSON тепер сховане за формою.
