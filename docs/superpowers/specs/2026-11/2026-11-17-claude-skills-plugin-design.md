# Скіли Obscura для Claude: локальний плагін

Дата: 2026-11-17
Статус: затверджено 2026-11-17
Spec-review: codex/gpt-6.1-sol @ 0703719 (author: claude) — 6 findings: 6 fixed, 0 rejected

## Для власника

### Мета

Автор пише оповідання з Claude, і чат веде його від задуму до готової книжки так, як це вдалося на «Десяточці». Питання ставляться по одному карткою, нічого не створюється без згоди автора, а модель під кожну задачу вибирається свідомо. Перший пакет — плагін для Claude Code з репозиторію. Пакування для збірки з MS Store — наступний окремий пакет (R-35, [#173](https://github.com/ysilvestrov/obscura-text-writer/issues/173)).

### Що зміниться для тебе

- **У репозиторії з'являється плагін `obscura`** з п'ятьма скілами:
  - `start-story` — від задуму до імпортованого плану;
  - `series-bible` — біблія циклу;
  - `draft-scene` — сцени в обох режимах твору;
  - `publish` — картка, обкладинка, експорт;
  - `setup-models` — моделі Obscura для режиму «obscura».

  Він не додає нових MCP-інструментів і не змінює сервер.
- **Встановлення — твій крок поза репозиторієм**, два рядки в Claude Code (див. «Встановлення» в тілі). Після цього скіли підхоплюються самі за змістом запиту або викликаються як `/obscura:start-story` тощо.
- **Як поводиться чат зі скілами:**
  - питає лише те, чого бракує, по одному питанню карткою;
  - твір створює, запуск у режимі «obscura» запускає, налаштування й картку змінює лише після твоєї згоди з підсумком;
  - пише короткий рядок про прогрес після кожного етапу й кожної сцени;
  - у кінці перелічує все, що вигадав сам.
- **Моделі.** Планування й чернетку робить найсильніша доступна модель. Хто робить завдання й пам'ять сцени, вирішить вимір на нейтральній сцені за правилом, записаним у тілі (§4). Окремого погодження цей вибір не потребуватиме.
- **Ручні сценарії — умова злиття.** PR, що додає скіл, проганяє його сценарій. Провал через поведінку скіла блокує PR, доки скіл не виправлено. Провал через інфраструктуру (сервер, мережа, ліміт) дозволяє повторний прогін із записом причини в журналі. Провал, який не повторюється у двох повторних прогонах, записується як нестабільність і не блокує.
- **Сайт інструкцій:** на сторінці «Чат-клієнти (MCP)» обома мовами з'являється розділ про встановлення скілів.
- **Незворотного** немає: плагін видаляється командою `claude plugin uninstall`, дані творів він не зберігає.

### На чому стоїть рішення

1. **Спершу — плагін для власника в Claude Code, потім — окремий пакет для Store.** `[вимога власника]` (17.11.2026)
2. **У першому пакеті чотири скіли з пропозиції 15.11 плюс `setup-models`.** `revise` відкладено. `[вимога власника]`
3. **`draft-scene` працює і в режимі «chat», і в режимі «obscura».** `[вимога власника]`
4. **Розподіл моделей у режимі «chat»:**
   - планування — найсильніша модель, з advisor, якщо він доступний;
   - чернетка — рівня Opus;
   - для завдання й пам'яті вибір між тією самою моделлю й дешевшим субагентом вирішує вимір.

   `[вимога власника]`
5. **Автора постійно інформують про прогрес.** `[вимога власника]`
6. **`setup-models` розпитує ціль і бюджет, а набір моделей бере з рецептів у самому скілі.** Ролі ставить по одній, зміни застосовує лише після згоди. `[вимога власника]`
7. **Готових пресетів ролей Obscura не постачає.** `GET /api/role-profiles` повертає лише збережені автором, а чат за MCP-BRIDGE не створює й не імпортує пресети. `[проба]` (П3)
8. **Список моделей провайдера через MCP можна отримати лише для вже налаштованої ролі.** `get_settings(models_for_role=…)` для порожньої ролі відповідає помилкою «Роль … ще не налаштовано». `[проба]` (П3)
9. **API-ключ чат не вводить і назву ключа не змінює.** Він бачить лише стан ключа: назву і джерело `env`/`store`, без значення (SECURITY-002, MCP-BRIDGE). `[проба]` (П3)
10. **Поля скіла, які розуміє лише Claude Code,** — `model`, `effort`, `context: fork`. Поза Claude Code (завантаження в claude.ai, Skills API) приймаються лише `name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools`, а пакет з іншими полями відхиляється. Поле `model` діє лише до кінця поточного ходу. `[проба]` (П1)
11. **MCP-сервер Obscura зареєстровано під назвою `obscura`.** Так його пишуть кнопка «Підключити Claude Code/Desktop» (`claude_connect.ENTRY = 'obscura'`) і сторінка сайту. Тож інструменти доступні як `mcp__obscura__*`. Для встановлення через `.mcpb` назва не перевірена. `[проба]` (П2)
12. **Субагент Claude Code не розмовляє з автором і не бачить розмови.** Він отримує лише своє завдання. Тому питання до автора лишаються в основній сесії, а субагентам дістаються лише кроки, для яких MCP віддає весь потрібний матеріал. `[виведення]`
13. **Матеріал етапів завдання й пам'яті сервер віддає повністю** через `get_stage_task`, тож субагентові не треба бачити розмову. Чи вистачає цього для якості, перевіряє вимір. `[виведення]`

### Ключові рішення

1. **Плагін живе в репозиторії й ставиться як локальний маркетплейс Claude Code.** Скіли мають версії разом із сервером, а пакет Store пізніше копіює ту саму теку. Відкинуто особисті скіли в `~/.claude/skills`: вони без версій, і оновлення сервера ламало б їх непомітно.
   - Розглянуто стандартне: методика всередині MCP (prompts чи інструмент-провідник) — відкинуто для цього пакета: це код сервера, весь текст займає контекст кожного клієнта, і вибору моделі він не дає. Лишається кандидатом на страховку в пакеті Store.
2. **У frontmatter лише переносні поля** (`name`, `description`, `metadata`). Розподіл моделей описано в тілі скіла як умовні інструкції: «у Claude Code — субагент з моделлю X, у Desktop Chat — порада автору змінити модель». Так один і той самий скіл піде і в Claude Code, і в ZIP для Desktop.
   - Відкинуто поле `model`: воно діє лише один хід, а книжка пишеться за багато ходів. До того ж claude.ai відхилив би такий пакет.
3. **Плагін не містить конфігурації MCP-сервера.** Сервер уже реєструє кнопка «Підключити до Claude» або ручна команда з сайту. Друга реєстрація з плагіна дублювала б запис і могла б вказати на інший порт (8765 проти налаштованого).
4. **Рецепти моделей у `setup-models` — довідковий файл скіла, а не код сервера.** Порядок такий:
   - скіл запам'ятовує поточні налаштування ролей;
   - записує роль із рецепта;
   - одразу звіряє модель з живим списком провайдера.

   Раніше звірити не можна: сервер не віддає список моделей для ролі, якої ще немає (П3). Якщо модель не підходить, а автор відмовився від заміни або звірка не вдалася, скіл повертає збережене значення ролі. Відкинуто вбудовані пресети в Obscura: це зміна коду й SPEC, окремий пакет. Відкинуто JSON-пресети в плагіні: вони потребують ручного імпорту, що важко недосвідченій людині.
5. **Тексти скілів англійською, тригери обома мовами, відповіді — мовою автора.** Англійською моделі найточніше виконують інструкції, а `description` містить фрази наміру українською й англійською. Відкинуто українські тексти скілів: англомовні користувачі Store отримали б інструкції, які гірше спрацьовують на їхні запити.

### Що стане гірше

- **Рецепти моделей застарівають.** Провайдери перейменовують і прибирають моделі, тож рецепт треба оновлювати. Застаріла модель на мить записується в роль до звірки. Після звірки скіл або пропонує заміну, або повертає попереднє значення, мовчки не лишає. Якщо сесія обірветься між записом і звіркою, неперевірене значення залишиться. Наступний запуск Obscura покаже його як неготовність, а не як мовчазну помилку.
- **Скіли не перевіряються автоматично повністю.** Структурні тести ловлять дрейф назв інструментів і полів. Поведінку (питання по одному, згода перед створенням) перевіряють сценарії `skill-creator`, які запускаються вручну.
- **Субагенти коштують окремо.** Кожен перечитує матеріал етапу. Вимір покаже, чи це дешевше за ріст контексту основної сесії.
- **Вимір і сценарії оплачуються з твого акаунта Claude.** Це окремі запуски `claude -p`: 9 прогонів виміру й по одному прогону кожного з шести сценаріїв.
- **Вибір моделі в Desktop Chat скіл лише радить.** Перемкнути модель там може тільки автор.
- **Новий тип артефакту в репозиторії.** Скіли — текст із поведінкою, тож зміни інструментів MCP тепер зачіпають і їх: SPEC вимагає оновлювати обидва разом.

## Тіло

### 1. Склад плагіна

```
integrations/claude/
  .claude-plugin/marketplace.json   # маркетплейс "obscura", один плагін
  obscura/
    .claude-plugin/plugin.json      # name "obscura", version, description
    skills/
      start-story/SKILL.md
      series-bible/SKILL.md
      draft-scene/SKILL.md          # + references/chat-pipeline.md, obscura-runs.md, continuity.md
      publish/SKILL.md
      setup-models/SKILL.md         # + references/recipes.md
    shared/rules.md                 # спільні правила; кожен SKILL.md посилається на нього
    evals/                          # сценарії skill-creator
```

Назву теки `integrations/claude/` обрав я. Вона лишає місце для інших клієнтів (Codex тощо) поруч. Скіл плагіна викликається як `/obscura:<skill>`. Тексти, що мають бути в кожному скілі, лежать у `shared/rules.md`, а SKILL.md посилається на нього через `${CLAUDE_PLUGIN_ROOT}`. Пакет для Desktop ZIP (наступний пакет) вбудує ці правила в кожен скіл.

### 2. Спільні правила (`shared/rules.md`)

- **Мова відповідей — мова автора.**
- **Питання — по одному**: картка `AskUserQuestion` (2–4 варіанти, рекомендований першим, власна відповідь завжди можлива). Без інструмента карток — одне питання текстом із пронумерованими варіантами.
- **Згода перед записом.** Нічого не створювати, не імпортувати, не запускати й не змінювати до згоди автора з підсумком. Згода стосується лише показаного.
- **Свої рішення позначати.** Усе, що чат вигадав сам (другорядні імена, назви, деталі світу), позначати як «моє рішення» і перелічувати в підсумку.
- **Прогрес:**
  - один рядок після кожного етапу і кожної сцени: що зроблено, що далі, скільки лишилося;
  - для фонових запусків — проміжний рядок при кожній зміні стану;
  - у кінці роботи — підсумок і перелік власних рішень.
- **Перший крок — перевірка сервера.** Інструменти `mcp__obscura__*` мають бути доступні, а `list_stories` — відповідати. Якщо інструментів немає або Obscura не запущено, скіл пояснює, як запустити застосунок чи підключити Claude (кнопка в бібліотеці або команда із сайту), і далі не йде.
- **Протокол сервера.** Правила revision, fingerprint і конфлікту 409 — з інструкцій сервера й `next_steps`. Скіл їх не дублює, а лише нагадує: «409 — прочитати знову».
- **Затвердження прози** в інтерфейсі Obscura лишається за автором. Скіл нагадує про це, коли сцена готова.

### 3. Скіли

#### 3.1. `start-story`

Тригер (дві мови): автор хоче написати оповідання чи книжку, має ідею, лор або план; «хочу написати», «не знаю, з чого почати», «write a story».

Ворота в цьому порядку, і лише те, чого бракує:

1. **Герої.** Для кожного головного героя:
   - вік або явне «усі учасники дорослі»;
   - кілька рис зовнішності;
   - заняття;
   - манера мовлення.

   Одна картка на одну прогалину. Другорядних героїв чат вигадує сам і позначає.
2. **Ідея, план, фінал.** Мінімум — ідея. Якщо плану чи фіналу немає, чат показує структуру: експозиція → зав'язка → розвиток дії → кульмінація → розв'язка. Для кожної відсутньої частини окрема картка з 2–3 варіантами.
3. **Обсяг.** За замовчуванням 7000 слів = 7 сцен по 1000: експозиція, зав'язка, три сцени розвитку дії, кульмінація, розв'язка. Картка з варіантами:
   - лишити 7×1000;
   - змінити обсяг чи кількість сцен;
   - об'єднати експозицію із зав'язкою;
   - об'єднати кульмінацію з розв'язкою.
4. **Назва.** Картка з 3 варіантами від чату.
5. **Лише якщо не сказано:** точка зору, місце й час, віковий рейтинг, мова. Для кожного пропонується значення за замовчуванням.

Якщо є лор, правила світу чи цикл, чат до першої книги пропонує `series-bible`.

Модель: найсильніша доступна. Advisor, якщо він є, — перед підсумком.

Завершення:
- підсумок: герої, сцени з роллю в структурі, назва, обсяг;
- згода;
- `create_story` → `get_templates` → `import_plan_and_characters` → `get_story`: перевірити `writing_mode` і серію;
- якщо режим «obscura», запропонувати `setup-models`, коли ролі не налаштовано.

#### 3.2. `series-bible`

- Біблія — окремий твір. Преамбула плану: «Серія: <назва>», «Номер: біблія». Кожна стаття — сцена: світ, магія, організації, раси тощо.
- Книги циклу мають «Серія: <назва>», «Номер: N». Факти біблії потрапляють у контекст пам'яті книги, а `get_story` показує статус серії.
- Статті пишуться конвеєром `draft-scene` без художніх подій: факти, шкали, правила.
- Перелік статей показується авторові й погоджується до створення.

#### 3.3. `draft-scene`

Тригер: план є, треба написати одну чи всі сцени, «пиши далі», «write the next scene».

Спершу `get_story` → `writing_mode` визначає гілку.

**Гілка «chat»** (`references/chat-pipeline.md`), порядок обов'язковий:

1. `get_stage_task(brief)` → `save_stage_result` з JSON `{objective, beats, constraints, proposed_changes, introduced}`.
2. `get_scene_context` → текст → `save_draft(expected_revision, context_fingerprint, draft_version_id)`. Для нової чернетки `draft_version_id` дорівнює `null`; наявну спершу прочитати й писати поверх.
3. `get_stage_task(edit)` → відповідь строго у форматі `result_format`, який задає режим редактора (`edit_mode`):
   - `prose` — повна відредагована проза;
   - `patches` — структуровані точкові правки за інструкцією етапу;
   - `diff` — програмні зміни за інструкцією етапу.

   → `save_stage_result`. Якщо сцена після цього потребує авторського перегляду правок (`needs_review` у `get_story`), скіл зупиняється, просить автора переглянути правки в Obscura й продовжує лише після його повідомлення. Те саме, коли сервер просить підтвердити попередню пам'ять.
4. `get_stage_task(memory)` → прочитати всі фрагменти частинами (`offset`, `max_chars` ≤ 20000) → JSON пам'яті за `result_format`.

Перед кожною сценою — контроль безперервності (`references/continuity.md`):
- час дії;
- хто присутній;
- що в руках і кишенях;
- стан героя;
- уже введені факти.

На редагуванні перевірити:
- латинські літери в кирилиці;
- кальки й русизми;
- деталі зовнішності, яких немає в картці.

Пастки для довідника:
- межі `max_chars`;
- назва поля `expected_revision`;
- «Спершу завершіть…» означає порушений порядок етапів.

**Гілка «obscura»** (`references/obscura-runs.md`). `start_run` запускає рівно один етап, тож сцена — це чотири запуски: `brief` → `draft` → `edit` → `memory`. Наступний етап визначає стан сцени з `get_story`.

Перед першим етапом сцени скіл пропонує карткою:
- «Покроково» — згода на кожен етап;
- «Усю сцену» — одна згода на чотири етапи з показаним сумарним переглядом.

Для кожного етапу:
1. `start_run(action, scene_id)` без `confirm` → перегляд: моделі, кількість викликів, попередження, бюджет.
2. Згода (або загальна згода на сцену) → `start_run(confirm=true)`, за потреби з `budget_limit_usd`.
3. `get_run` до завершення, з рядком прогресу на кожну зміну стану.
4. `get_scene_text` → один рядок підсумку.

Зупинка й рішення автора:
- **після `brief`:** у режимі «Покроково» показати завдання і спитати, чи писати чернетку;
- **після `edit`:** якщо потрібен перегляд правок або підтвердження пам'яті, попросити автора зробити це в Obscura й чекати;
- **запуск не вдався, скасований або перевищив бюджет:** показати причину й не запускати наступний етап без нової згоди.

Якщо ролі не налаштовано, скіл зупиняється й пропонує `setup-models`.

**Розподіл моделей (гілка «chat»):**

| Крок | Claude Code | Desktop Chat |
|---|---|---|
| brief, memory | за результатом виміру (§4): або в основній сесії, або субагент з моделлю з виміру | в основній сесії |
| draft | Opus-рівень: якщо модель сесії слабша, субагент `model: opus` із завданням «прочитай контекст сцени, напиши, збережи» | порадити автору вибрати найсильнішу модель |
| edit | як draft | як draft |

Субагенту передаються `scene_id`, вимоги до стилю, рішення автора з розмови, що стосуються сцени, та очікуваний результат. Питань автору субагент не ставить.

#### 3.4. `publish`

Тригер: усі сцени мають прозу, або автор просить опублікувати чи експортувати.

1. **Картка:** `get_publication` →
   - **автор** — обов'язкове питання: картка з іменами з довідника підписів плюс нове ім'я через `add_signature`. Не вигадувати й не брати мовчки;
   - **анотація** — 2–3 речення без спойлера фіналу, на погодження;
   - **жанри** — 1–3 коди FB2, карткою;
   - **ключові слова** — до 10;
   - **цикл і номер** — із серії;
   - `update_publication(expected_revision, лише змінені поля)`.
2. **Обкладинка.** Картка з палітрою: «Чорнило», «Папір», «Бордо», «Ліс» (`ink`, `paper`, `wine`, `forest`) → `generate_cover(story_id, palette)` → `update_publication({cover_id})` → показати результат і запропонувати іншу палітру.
3. **Експорт.** Картка з форматом (FB2 / EPUB / PDF) → `export_book` або шлях в інтерфейсі ☰ «Дії твору» → «Експорт…». Для FB2 потрібні автор і жанр.

#### 3.5. `setup-models`

Тригер: твір у режимі «obscura» без налаштованих ролей; автор питає, яку модель вибрати; `start_run` повертає неготовність ролей.

1. `get_settings` — що налаштовано, стан ключів, власні пресети автора.
2. **Ціль**, по одній картці:
   - жанр і рейтинг (чи потрібні моделі без цензури);
   - бюджет на книжку (дешево / баланс / якість);
   - провайдер, для якого вже є ключ.
3. **Ключа немає** — пояснити, де його вписати в інтерфейсі Obscura (налаштування твору → моделі), і чекати. Ключ у чаті не приймати; якщо автор надіслав його в чат, попросити вписати в інтерфейсі.
4. **Є власний пресет**, що підходить — запропонувати його: `apply_role_preset` без `confirm` → перегляд → згода → `confirm`.
5. **Інакше рецепт** із `references/recipes.md`: ціль → провайдер і модель для кожної з чотирьох ролей. Провайдер у ролей може бути різним.
6. **Одна згода на весь рецепт.** Автору показується таблиця «роль → модель, тариф» і що буде далі: ролі записуються, потім звіряються з живим списком, а якщо моделі в списку немає, буде окреме питання. Згода стосується лише показаної таблиці.
7. **Запис і звірка.** Спершу зберегти з `get_settings` поточні поля кожної ролі. Далі для кожної ролі:
   - `update_settings(section=роль, {provider, model})`;
   - потім `get_settings(models_for_role=роль, models_query=<точний id моделі>)` перевіряє точний збіг `id`, тариф і `uncensored`.

   Записати модель до перевірки доводиться: сервер не дає звірити роль, якої ще немає (П3). Налаштування моделі не викликає.
8. **Моделі немає або вона не підходить.** Невідома модель, `uncensored=false` для рейтингу, що потребує моделі без цензури, або тариф вищий за бюджет. Тоді:
   - **пошук заміни:** окремий широкий запит `models_for_role` із фільтром за родиною моделі з рецепта (наприклад, `deepseek`, `llama`), а якщо порожньо — без фільтра. Відповідь обмежена 200 моделями, тож при `models_total` > 200 скіл звужує фільтр, а не робить висновків з неповного списку;
   - картка з 2–3 найближчими моделями (та сама родина й розмір, тариф у бюджеті, `uncensored` за потреби) → згода → `update_settings`;
   - **відкат:** автор відмовився, замін немає або звірка не вдалася → `update_settings` повертає збережені поля ролі. Для ролі, якої раніше не було, автору повідомляється, що вона лишилась із неперевіреною моделлю, і як її змінити в інтерфейсі.
9. **Підсумок:** `changed` усіх ролей і тарифи.

Рецепт має провайдера зі стандартною назвою ключа (`OPENROUTER_API_KEY`, `VENICE_API_KEY`), бо чат `key_env` не встановлює.

**Джерело рецептів — моє рішення.** Перший варіант рецептів у PR 2 складає виконавець:
- за основу береться робоча конфігурація власника, наприклад `venice / deepseek-v4-1-flash-1017-uncensored` для режиму «obscura»;
- варіанти звіряються з живими списками моделей OpenRouter і Venice: тариф, контекст, `uncensored`.

Кожен рецепт має дату перевірки. Власник переглядає таблицю рецептів у PR, як звичайний код.

### 4. Вимір розподілу моделей

**Мета:** вирішити, хто в Claude Code робить brief і memory у гілці «chat».

**Ізоляція від бібліотеки власника.** Вимір не чіпає зареєстрований на рівні користувача сервер `obscura`. Виконавець:
- запускає окремий сервер Obscura з текою даних у `C:/tmp/<назва>` на вільному порту;
- проганяє кожен варіант у headless-сесії `claude -p --mcp-config <файл> --strict-mcp-config --model <модель> --output-format json`, де файл описує `obscura` → міст до тестового сервера;
- бере вартість і токени з JSON-результату (`total_cost_usd`, `usage`).

Тож вимір виконує виконавець сам, без кроку власника. Платить він з акаунта Claude власника (див. «Що стане гірше»).

**Процедура:**
1. Нейтральна тестова сцена на тестовому сервері.
2. Brief і memory однієї сцени тричі кожним варіантом:
   - (A) основна сесія, яка вже має чернетку в контексті;
   - (B) субагент `sonnet`;
   - (C) субагент `haiku`.
3. **Еталон незалежний від моделей.** Виконавець заздалегідь складає з тексту тестової сцени й плану:
   - перелік обов'язкових фактів пам'яті (хто, що, де, зміни стану, смерті, предмети);
   - обов'язкові пункти завдання (`objective`, ключові `beats`, `introduced`).

   Еталон записується в журнал до першого прогону.
4. Записати для кожного прогону:
   - вхідні й вихідні токени та вартість;
   - відмови `save_stage_result` (помилки схеми, порядку);
   - для пам'яті й завдання за еталоном: пропущені обов'язкові пункти, вигадані факти (немає в тексті) і суперечності з текстом.

**Правило вибору:** найдешевший варіант, у якого за три прогони:
- жодної відмови схеми;
- жодного вигаданого факту чи суперечності;
- не більше одного пропущеного обов'язкового пункту на прогін.

Якщо (A) сам не проходить це правило, проблема в конвеєрі, а не в розподілі. Тоді вимір зупиняється, а вибір виноситься до власника. Результат і числа записуються в журнал виконання і в `references/chat-pipeline.md`. Вибір із цього правила не потребує окремого погодження власника.

Ручні сценарії лежать в `integrations/claude/obscura/evals/` і запускаються через `skill-creator`. Вони проганяються тим самим ізольованим способом, що й вимір (§4): тестовий сервер у `C:/tmp`, `claude -p` з `--strict-mcp-config`. У traceability записується процедура і причина: поведінка моделі не детермінована для pytest.

**Що означає «готово» для S04–S09 (моє рішення).** PR, що додає скіл, проганяє його сценарій щонайменше один раз:
- S04 і S05 — у PR 1;
- S06–S09 — у PR 2.

Результат прогону (дата, коміт, пройдено чи ні, що пішло не так) записується в журнал виконання. У `docs/STATUS.md` він не потрапляє: `verify.py` запускає лише автоматичні тести, а ручний прогін не видається за їхній результат. Сценарій, що не пройшов через поведінку скіла, блокує свій PR, доки не виправлено скіл. Провал через інфраструктуру (сервер, мережа, ліміт акаунта) дозволяє повторний прогін із записом причини. Провал, що не повторюється у двох повторних прогонах, записується в журнал як нестабільність, а PR не блокує.

MCP-BRIDGE отримує речення: перейменування чи видалення інструмента вимагає оновити скіли (S03).
